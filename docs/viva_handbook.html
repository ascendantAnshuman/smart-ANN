The one-minute answer

If you say nothing else, say this:

"What is your project?"

A phone answering questions with AI has to search a vector index and then run a language model. Both cost battery and time. But a phone throttles when it gets hot, loses CPU to other apps, and drains — so a fixed configuration is wrong almost all the time: too slow when the device is stressed, needlessly expensive when it isn't.

SMART-ANN measures the device's real state — temperature, CPU pressure, battery — and changes how hard the retrieval searches, at runtime, to stay inside a latency or energy budget. I built it, measured it on a real Android phone, and tested the baseline's claims rather than assuming them.

Then offer the hook that makes them ask more: "Two of my three main findings are negative — including one that identifies a missing term in the baseline paper's cost model."

1 · The problem

Why on-device RAG at all

Retrieval-Augmented Generation grounds a language model in a document corpus: retrieve relevant passages, put them in the prompt, generate an answer. Doing it on the phone rather than in the cloud buys privacy (documents never leave the device), offline operation, and no per-query server cost.

Why a phone is not a small server

  • Thermal throttling. Sustained load raises temperature; the SoC then reduces clocks. Measured on the target handset: skin temperature rose 32.9 → 37.5 °C over a 25-minute retrieval workload.
  • Contention. Other apps take CPU unpredictably.
  • Battery. Every query costs measurable energy — 99.28 mJ all-in on the target device.
  • Heterogeneous cores. The target SoC has three clock domains, and one instant sample showed four cores at ratios 1.00, 0.61, 0.22 and 0.27 simultaneously.

A static configuration must be tuned for the worst case (wasting capability most of the time) or the average case (missing its budget under stress). That gap is the opportunity.

2 · The MobileRAG baseline

MobileRAG (arXiv:2507.01079) is the paper this project builds on and tests. Two components matter:

EcoVector

A memory-efficient ANN index for phones. The corpus is partitioned into Nc clusters by k-means. A small HNSW graph over the centroids stays in RAM; the per-cluster vectors live on disk and are loaded only when that cluster is probed. This keeps resident memory far below the corpus size.

Selective Content Reduction (SCR)

Before generation, trim retrieved passages to the parts most relevant to the query, cutting prompt tokens and therefore generation cost.

The claim I tested

MobileRAG argues EcoVector beats IVF-on-disk when

ef_L · M'  <  N / N_c

— i.e. when a per-cluster HNSW graph walk touches fewer vectors than a flat scan of that cluster. For SIFT1M, N/N_c = 4000, so the condition holds by a wide margin and per-cluster graphs should win. They do not. Finding 1 explains why.

4 · Architecture

The two-phase search

The index splits retrieval so the controller can decide after seeing cheap evidence but before paying the expensive part:

probe(q, cfg)Searches the in-RAM centroid graph. Returns candidate cluster IDs, their distances, and cheap query features. Costs well under a millisecond.
finish(q, probe, cfg)For each selected cluster: load from disk → search → unload → merge results. This is where nearly all the cost lives.

Why it matters: a controller can look at probe output and decide how many clusters to actually open. There is no rerank stage — it was specified, then removed once measurement showed the exact distances were already available from the cluster search, so reranking would recompute what was known.

Cluster storage

Clusters are stored flat (.npy, memory-mapped) rather than as per-cluster HNSW graphs. That is a measured decision, not a default — see Finding 1.

The control layer

StaticPolicyFixed config. The tuned baseline — grid-searched per scenario, never crippled.
AimdPolicyAdditive-increase / multiplicative-decrease on nprobe, like TCP congestion control. Has a control_period_s — the parameter whose absence caused the collapse.
BudgetPolicyReads a table of measurements (not the cost model) and picks the highest-recall level whose measured p95 fits the latency budget.
DeviceStatePolicyC5. Derates the budget on temperature, thermal slope, battery level, throttling. Refuses to act on NaN — "not measured" is not "cold".
EnergyBudgetPolicyC4. Integrates V·I·dt from a live source. honours_energy_budget() returns True only when a real source is wired in and declared.

Why the budget policy looks up instead of predicting

The Phase 3 cost model holds at 14.75% MAPE inside its fitted regime and fails at 35.87% outside it, because cpu_util saturates at 1.0 — 12,469 contended samples pinned at exactly 1.000 while latency spanned 41×. A policy predicting from that model would be most confident exactly where it is most wrong, which is the situation the project exists to handle. So the policy reads measured percentiles instead.

7 · Method and the rules

Six rules were fixed before any code was written. They are the reason the defect list exists.

  1. Never fabricate numbers. No plotting script may contain a hardcoded result, example data, or a placeholder. Missing data must fail loudly.
  2. No silent stubs. Anything unimplemented raises NotImplementedError with a reason and appears in TODO.md. Never a plausible dummy value.
  3. The baseline must be tuned, not crippled. Per-scenario grid search.
  4. Every result reproducible from (config, seed). Each run writes a manifest with git SHA, config hash, library versions, hostname, seed, wall-clock bounds.
  5. Controller overhead is itself a measured metric. A control layer costing more than it saves is a negative result.
  6. Ask before adding a dependency.

The capability gate

Every telemetry source publishes a capability table saying what it can and cannot measure. assert_manifest_consistent() refuses any run manifest claiming a measured value for a field the table calls unavailable. This is a gate, not a log — a false claim cannot reach the parquet.

Recall, done carefully

Recall is score-equality (tie-aware), not index-overlap: when several vectors sit at identical distance, which IDs get returned is arbitrary, so counting ID matches penalises correct answers. The tolerance band is atol + rtol·|threshold|, sized from measurement rather than guessed.

A convention that bites

hnswlib's ip space returns 1 − inner_product, and its l2 space returns squared distance. Distances can legitimately be negative — NYTimes reaches −1.918×10⁻⁷. Any assertion that distances are non-negative is wrong, and no code path may take a sqrt, log or division that assumes otherwise.

"Why does the model fail under contention?"

cpu_util is a censored feature. It saturates at 1.0, so it cannot express contention magnitude: 12,469 samples all read exactly 1.000 while the latency they were supposed to explain spanned 41×. The model has no variable left to move. That is why the budget policy reads measured percentiles rather than predicting.

The energy model was correctly refused

Phase 3's energy coefficients (3.85 V, 2300 µA CPU, 800 µA I/O) are MobileRAG's reported values for their device — not fitted here. Finding 2 — the control law collapsed

Look at the quiet rows. With no disturbance at all, the adaptive policy sat at minimum effort (nprobe 1 against static's 16), missed the target more often than static, and gave up 0.418 recall for nothing.

Diagnosis: the control period was shorter than the observation delay. The policy acted, then acted again before its previous action could appear in the rolling p95 it was reading. Every action looked ineffective, so it kept decreasing. This is structural, not a tuning error — it's the same reason TCP paces congestion window per round-trip time, not per acknowledgement.

Confirmed by pre-declared test: the diagnosis was written down with its predicted outcome before the confirmatory run.

Reduction is not free at any level — every confidence interval excludes zero, including the mildest. But the trade-off is smooth and monotone, which is what a controller needs: keep1 buys a 47% cut in generation latency for a 14% relative F1 loss.

The finding that decides whether SCR is worth having

SCR's own cost is ~8 ms warm but ~1220 ms p95 cold on the query path, because it embeds every window of every retrieved chunk at query time. Those two numbers bracket the question: on-path it costs roughly 4× what it saves and cannot pay for itself; warm it is a clear win.

The difference is when window embeddings are computed — and the corpus is static, so they could be computed once at index time. That is an implementation choice, not a property of the method. Recorded rather than acted on, because it would move the cost model's dominant term.

"How did you choose the reduction levels?"

From measurement, after the first attempt failed. I sampled 3,000 SQuAD chunks: 1.4% hold one sentence, 22.6% two, 76.0% exactly three. At a 2-sentence window a chunk yields at most two windows — so "keep the top 3" keeps everything, and three of my four arms came back byte-identical to the baseline. The reducer wasn't broken; the ladder was. Rebuilt at window size 1, which is the only setting with real dynamic range on this corpus.

12 · Joint vs split control (Phase 8)

A 3×3 grid: nprobe ∈ {1, 4, 16} × SCR ∈ {off, keep2, keep1}, 250 questions per cell, cells interleaved round-robin.

Declared before the run: C3 is supported if some joint cell is not dominated by any single-dimension cell — at least as accurate and at least as cheap.

Result: 3 joint cells sit on the Pareto front. But the shape matters more than the verdict — no joint cell dominates the best single-dimension cell outright. The highest F1 is still retrieval-only at maximum effort. What joint control does is extend the frontier downward in cost, reaching operating points at 516–804 ms that neither dimension reaches alone. That is exactly the region an adaptive controller occupies under pressure.

This is the second verdict this experiment produced

The first run also said "C3 supported" — and it was an artifact. One generation took 20.4 minutes (the host slept), dragging that cell's mean cost to 6× its median; and I had run the cells in blocked order, so identical work cost 1.01 ms/token early and 1.96 ms/token late. Both single-dimension baselines sit at the highest nprobe — measured last, therefore slowest — so the drift inflated exactly the cells the joint cells were compared against.

Re-run interleaved with median cost: ms/token spread fell to 1.11×, and the verdict survived with a different cell set. A right answer from a broken measurement is indistinguishable from a right answer.

13 · On the device

vivo I2304, Android 16, arm64-v8a, Snapdragon, 8 cores in 3 clock domains.

Two findings before a single measurement

hnswlib builds successfully and then crashes

It compiles in 19 s, pip reports success, exit code 0 — and import hnswlib dies with SIGILL before executing a line. setup.py compiles with -march=native, and clang emitted an instruction this core lacks. HNSWLIB_NO_NATIVE=1 fixes it completely. Both builds exit 0; only running the code distinguishes them.

HNSW index files do not transfer

load_index refused the pushed graph. Not a truncated transfer — the file is byte-identical on both machines, same SHA-256. The writer is chroma-hnswlib 0.7.5, the reader upstream hnswlib 0.8.0, and neither can move to meet the other. Only the centroid graph is unportable (everything else is .npy), so it is rebuilt on-device in 0.016 s — and equivalence was checked: host and device both score recall@10 = 0.9543 on the same 300 queries.

"Your R² is only 0.30. Isn't that a bad model?"

It is honest, and the sweep is the answer. The differencing window moves R² sixfold, so reporting one row would hide that the result depends on a choice no reader would question. The 120 s row scores highest and I excluded it: eleven points against three free parameters flatters itself.

What convinces is stability: τ stays 67–107 s and a stays 5.9–9.4e-04 across every window while R² swings from 0.11 to 0.69. Point estimates that barely move across analysis choices are stronger evidence than any single goodness-of-fit.

Short windows fail for a measurable reason: skin rose ~0.003 °C/s, while 3-second differencing yields a dT/dt whose standard deviation is 0.051 °C/s — sixteen times the signal. The sensor quantises at ~0.005 °C, so short differencing measures quantisation, not physics.

Why τ = 68 s is the most useful number in the project

It is the thermal observation delay. Phase 6's control law collapsed because its control period was shorter than its observation delay. This says any thermally-aware controller sampling faster than ~68 s reproduces that collapse — and now there is a measured number saying so instead of an argument.

The number I refused to report

Marginal energy per cluster fits at R² 0.415 and returns an idle power of −0.209 W. A phone idling at negative 209 milliwatts does not exist.

Work rate spans 95–251 clusters/s and never approaches zero, so the intercept extrapolates 95 units past the nearest observation. Independently: at the trace's mean effort the marginal term predicts 115 mJ/query against a measured all-in average of 99.3 mJ/query — the marginal exceeds the total, with the negative intercept absorbing the difference.

It is computed, recorded as reportable: false, and printed with its reasoning. The fix is an experiment change, not an analysis change: duty-cycle the trace so the baseline is measured rather than extrapolated. That instrumentation is built and tested; what remains is 20 minutes of handset time.

"How do you know negative current means discharge?"

Calibrated, not assumed. Three phases — idle / load / idle — on battery, sampling every 3 s. All 40 samples negative while discharging, no exceptions. Load cost −419 mA against the pre-baseline and −497 mA against the post; the idle drift between the two baselines was +78 mA, which is why both were measured.

And cross-checked two independent ways: the coulomb counter fell 19,000 µAh over 148 s (= 462 mA mean) while integrating the current sensor gave 524 mA. Within 12%, neither derived from the other.

14 · The three findings

Finding 1 — MobileRAG's per-cluster graphs do not pay

The paper's condition ef_L · M' < N/N_c predicts per-cluster HNSW graphs should win comfortably (SIFT1M: N/N_c = 4000). Measured, they lose.

Why: a missing term. The paper prices cluster access as pure I/O — bytes read from disk. Measurement shows deserialisation is 95–99% of the load cost. Materialising a graph structure costs far more than materialising a flat array, and the paper's model has no term for it. The condition is right about comparisons and silent about materialisation.

This is the sharpest framing: not "graphs are bad" but "the published cost model omits the dominant term."

Finding 2 — the control law collapsed, and the diagnosis is structural

Control period shorter than observation delay ⇒ the controller acts before it can see its previous action ⇒ every action looks ineffective ⇒ monotone decrease to the floor. Pre-declared and confirmed. The fix is a control period, and Phase 4 now supplies the measured delay it must exceed for thermal control: 68 s.

Finding 3 — context reduction is not free, and SCR cannot pay for itself as implemented

Every reduction level costs answer quality significantly (all CIs exclude zero). And SCR costs ~1220 ms on the query path to save ~300 ms of generation. The escape is precomputation, not adaptation — the corpus is static.

15 · The 22 defects and seven detection mechanisms

Every one was caught before it produced a reported number. Ranked by how likely each was to survive undetected, which is not the same as severity.

The most instructive ones

#2A generated conclusion carried a hardcoded verdict beside computed numbers — it printed "the control law does not work" next to a negative recall cost. No test asserts on English.
#3The static baseline was not tuned and the manifest said it was. Selection met the target by construction, because the target was derived from the same row.
#4compute_topk dropped ‖q‖², making every ground-truth distance wrong by a per-query constant — and plausible.
#6Uncapped ef·M overstated work by up to 29.5×, on the field the cost model regresses against.

16 · Interview Q&A

Scope and novelty

"What's novel here? Adaptive systems aren't new."

Correct — AIMD is from TCP, thermal throttling is standard. The novelty is the application and the measurement: nobody has published measured energy and thermal cost per unit of ANN retrieval effort on a real handset, tied to a control loop with a measured observation delay. And the by-product is a correction to a published cost model.

"Isn't this just engineering?"

The engineering is the instrument. The research output is three findings — two negative — that change what someone should build: per-cluster graphs don't pay because of a missing materialisation term; a thermal controller must respect a 68-second observation delay; and SCR as commonly implemented costs more than it saves unless embeddings are precomputed.

Method

"How do you know your baseline isn't strawmanned?"

Rule 3 was fixed before any code: the static baseline is grid-searched per scenario. And it was audited — defect #3 caught a version where max(key=...) returned the largest candidate unconditionally and the target was derived from that same row, so selection met the target by construction. Fixed by anchoring the target on the median candidate.

"Why should I believe your timings?"

Because I stopped believing them four times. Background load corrupted measurements repeatedly, so the acceptance script now samples CPU for the whole run and exits with a distinct code (2, not 1) if more than 10% of samples exceed threshold — a contaminated run is the absence of a result, not a result. Configurations are interleaved round-robin, never blocked, because a blocked sweep measures machine drift as much as code.

"Your sample sizes?"

n=1000 questions for answer quality with 10,000-resample paired bootstrap; 250 per cell for the joint surface; 19,144 and 15,425 queries for the device traces; 3,829 per effort level in the device sweep. Where n is small — the 11-point thermal window — I say so and exclude the result.

Technical detail

"Explain your recall metric."

Score-equality (tie-aware) recall@k. When multiple vectors share a distance, which IDs are returned is arbitrary, so index-overlap recall penalises correct answers. I compare distances against ground-truth distances with a combined tolerance atol + rtol·|threshold|, sized from measurement. Duplicate retrieved IDs are rejected outright.

"Why nprobe and not ef_search?"

Measurement narrowed it. ef_centroid is effectively free — the centroid graph is tiny — and ef_list turned out inert given flat cluster storage. So the action space is one-dimensional by measurement, and I state C1 as "adaptive retrieval effort" rather than "several ANN parameters". That narrowing is itself a result.

"What is τ and where does it come from?"

The thermal time constant of a first-order lumped-mass model: dT/dt = a·work + b·(T − T_ref) + c, with τ = −1/b. It says how long a change in retrieval effort takes to appear in temperature. Fitted from a 25-minute device trace, τ = 68 s, stable across every differencing window.

Limitations — volunteer these

"What are the limitations?"
  • One device. All device results are from a single vivo I2304. Thermal constants are device-specific by nature.
  • C4 half. Energy is measured; per-query attribution needs a duty-cycled trace.
  • C5 unproven. Policy and tests exist; no experiment against live telemetry.
  • Cost model fails under contention (35.87% MAPE) because cpu_util is censored.
  • NYTimes footprint 11.6× the paper — open, recorded, unexplained.
  • freq_ratio is a scalar and the SoC has three clock domains. Unresolved by choice, because the fix changes what the controller may claim.

17 · The hardest questions

"You found the baseline's model is wrong. Are you sure it isn't your implementation?"

Fair, and it's why the footprint check exists. SIFT1M's measured resident memory lands within 1.24× of MobileRAG's published Figure 6 — independent evidence the index is built correctly. If my implementation were broken, that number wouldn't land near theirs. Separately, the materialisation cost is measured directly per stage, not inferred from the discrepancy.

"Your adaptive policy is worse than static on recall. Doesn't that defeat the point?"

Under contention it cut SLO violations from 28.2% to 6.3% — that's the trade, and it's the intended one. But in the quiet phase it was worse on both axes, and I report that as a failure of the control law, diagnosed structurally. The mechanism works; the first control law was wrong; the fix is a control period no shorter than the observation delay, which I have now measured.

"You reported 7/7 verification earlier and it was 6/7. Why should I trust the current number?"

Because I found that myself and wrote it down. The data-status check was routed through a broken entry point that exited 0 while doing nothing. It's now fixed, the entry point is tested as a subprocess (an in-process test runner cannot catch it), and verify_all.py fails any step producing no output at all — an exit code is a claim, output is evidence.

"Why is one acceptance check failing?"

Deliberately. NYTimes check 4 fails because of a cluster-miss property of that dataset, not a defect. The verification expects exit 1 there. A verification demanding exit 0 could only be satisfied by hiding a real result — and the earlier version used a boolean "ignore the code" flag that tolerated every outcome, including a timeout. That was defect #16.

"How much of this is reproducible?"

All of it, from (config, seed). Every run writes a manifest with git SHA, config hash, library versions, hostname, seed and wall-clock bounds. scripts/verify_all.py re-runs seven steps through the documented entry points — tests, lint, types, data status, index acceptance, cost fit, figures — and currently reports 7/7 with a recorded machine-load profile proving the run was uncontaminated.

"What would you do with six more months?"
  1. Finish C4's per-query attribution — instrumentation is built, it needs one run.
  2. Run C5 against live telemetry, with a control period ≥ 68 s.
  3. Precompute SCR window embeddings at index time and re-fit — that alone may flip SCR from a loss to a win.
  4. Replicate on a second handset, since thermal constants are device-specific.
  5. Resolve freq_ratio to a per-cluster vector and re-examine what the controller can claim.
