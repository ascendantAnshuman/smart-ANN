09-09-2026SCOPE2

Aim

To build and measure a runtime control layer that lets an on-device RAG system decide how much retrieval effort to spend on each query, using the live state of the device, instead of running one fixed configuration chosen at build time.

A fixed configuration has to be tuned either for the worst case, which wastes recall almost all of the time, or for the average case, which then misses its latency budget exactly when the phone is hot, busy with other apps, or low on battery.

To find out what that adaptation is actually worth, by measuring temperature, energy and latency on a real handset rather than estimating them from a datasheet.

Every claim is reproducible from a config file and a seed. The controller's own overhead is measured and reported as a metric in its own right, rather than being assumed small.

Scope note. The on-device half of the system is retrieval. Answer generation runs on the host machine, not on the handset.

Baseline: MobileRAG (arXiv:2507.01079).  ·  Target device: vivo I2304, Android 16.

09-09-2026SCOPE3

Abstract

Running RAG on the phone itself gives privacy, offline operation and no per-query server cost. But a phone is not a server. It throttles when it gets hot, shares the CPU with other apps, and discharges. Every published on-device RAG system still ships a retrieval configuration that is fixed once, at build time.

This project reimplements the EcoVector index and splits search into two parts: a cheap probe that picks candidate clusters, and an expensive finish that loads and searches them. The gap between the two is where a decision can be taken, per query, while the expensive work is still uncommitted. Five control policies use live thermal, CPU and battery telemetry to make that decision.

The system is evaluated on SIFT1M, NYTimes and SQuAD, on a laptop and on a vivo I2304 handset, with temperature and energy measured on the device itself.

Three principal findings, two of them negative:

  • MobileRAG's condition for using per-cluster graphs holds by about 4000×, and the graphs still lose. The published cost model leaves out deserialisation, which we measured at 95–99% of load cost.
  • The first control law collapsed to minimum effort with no disturbance present at all. The cause is structural: its control period was shorter than the observation delay, later measured at 68 s.
  • Content reduction is not free at any level. Every confidence interval excludes zero.

Energy was measured on battery at 3.206 mJ per cluster, with the idle baseline cross-checked two independent ways to within 7.9%. Retrieval accounts for about 19.5% of a query's 131 mJ, which is a smaller claim than the literature usually makes, and one we can defend.

09-09-2026SCOPE6

Research Gap

G1 — On-device retrieval is open-loop. MobileRAG and EdgeRAG both fix the retrieval configuration ahead of time. Neither one looks at temperature, contention or battery while it is running.

We address this by putting a control decision between probe and finish, driven by live telemetry (O1, O5).

G2 — Published cost models are untested on handset storage. The conditions are stated as comparison counts and validated on servers. Nobody measures what it costs to materialise an index structure from phone flash, as distinct from reading its bytes.

We address this by measuring load cost on the handset and separating deserialisation from I/O.

G3 — Energy is modelled, not measured. On-device energy figures come from datasheets or reference current models, not from a battery, per unit of retrieval work, with the idle baseline separated out.

We address this by duty-cycling the workload so the idle baseline is observed rather than extrapolated (O4).

G4 — Feedback delay is not a design parameter. The interval between a control action and its appearance in the controlled signal is never measured. A controller faster than that interval is unstable, for reasons settled decades ago in networking.

We address this by fitting a thermal model on the device and reporting the measured delay as a design constant (O5).

G5 — Content reduction is not priced in answer quality. Prompt compression reports token and latency savings, rarely against a byte-identical control on a corpus that has gold answers.

We address this by scoring every reduction level against a byte-identical passthrough on SQuAD (O2).

Objectives

O1 (C1) — Adapt retrieval effort at runtime. Two-phase search plus policies that pick the effort for each query. Measured by: violation rate under induced contention, with controller overhead reported.  →  G1

O2 (C2) — Adapt content reduction and price it in quality. Compared against a byte-identical passthrough control. Measured by: EM and F1 against passthrough, with paired bootstrap confidence intervals.  →  G5

O3 (C3) — Test whether joint control beats separate control. A 3×3 surface, with the criterion declared before the run. Measured by: Pareto domination.  →  G1, G5

O4 (C4) — Measure energy on the device. A duty-cycled trace, so the idle baseline is observed rather than extrapolated. Measured by: marginal mJ per cluster with a confidence interval excluding zero, and a physically sensible intercept.  →  G3

O5 (C5) — Adapt to thermal and battery state. Fit a thermal model, obtain the observation delay, and test against a tuned static baseline. Measured by: violations and recall, with the same effective budget in both arms.  →  G1, G3, G4

09-09-2026SCOPE9

Functional Requirements

  • Corpus preparation. Download each dataset, check it against a recorded SHA-256, split the text into chunks, embed them, and load the exact ground-truth neighbours and distances.
  • Index construction. Partition the vectors into clusters, build the centroid graph, write the clusters to disk, and record the build in a manifest keyed by the config hash.
  • Two-phase search. probe() returns candidate clusters and cheap query features. finish() loads, searches and unloads them. The control decision sits between the two.
  • Device telemetry. Sample temperature, clock frequency and battery on a background thread, and publish a capability table that states what can actually be read on this device.
  • Control policies. Choose the effort level and the reduction level for each query, and record the decision, the inputs it used, and how long it took to make.
  • Content reduction. Score sentence windows against the query and keep the best ones. When reduction is disabled the prompt must be byte-identical to the unreduced one.
  • Generation and scoring. Build the prompt, generate the answer, and score Exact Match and token-F1 against the gold answer.
  • Record keeping. One parquet row per query holding latency, recall, config, overhead and provenance, plus a run manifest with the commit, config hash, library versions, host and seed.
  • Model fitting. Fit the latency, thermal and energy models, and refuse to report any coefficient that the data does not actually support.

MobileRAG's condition for preferring per-cluster graphs holds by a wide margin. The condition ef_L · M′ < N/Nc gives 4000 for SIFT1M, and the graphs still lose, by 2.5 to 2.8× at every matched recall point. Recall is effectively identical across all three (0.6487–0.6507 up to 0.9783–0.9807), so this is a fair comparison.

The graphs do save distance comparisons exactly as predicted, 2,298 against 8,784 at the first point. They lose anyway.

Why. The published condition counts distance comparisons and prices cluster access as pure I/O. Measured on the handset, 95–99% of load cost is deserialisation, which is a term the model does not contain. Materialising a graph costs far more than materialising a flat array.

Deserialisation: turning the stored bytes on flash back into a usable in-memory structure, as opposed to simply reading those bytes.

Consequence for the design. Cluster payloads in SMART-ANN are flat and memory-mapped. This is a measured decision, not a default. Cost model: 14.75% MAPE on quiet data against a 15% target, but 35.87% on contended data, because the CPU-utilisation feature saturates at 1.000 for 12,469 samples while the latency it has to explain spans 41×. That is why the budget policy reads measured percentiles instead of predictions.

C1 — the intended result is one row. Under contention, violations fall from 28.17% to 6.27%. Everything else on that table is the finding. In the quiet phase, with no disturbance at all, AIMD sat at nprobe = 1, missed the target more often than static (6.09% against 0.66%), and gave up 0.418 recall for nothing.

The recovery row is the proof. Static returns to 0.08% once contention lifts. AIMD stays at 5.62% and never climbs back. A working controller recovers; this one has no path up. The cause is that its control period was shorter than the observation delay, so every action looked ineffective and it decayed steadily to its floor. This is the same condition that makes TCP pace per round-trip time rather than per acknowledgement.

C2 — reduction is not free at any level. Every ΔF1 interval excludes zero, including the mildest one. But the trade-off is smooth and monotone, which is what a controller needs: keep1 buys about a 47% cut in generation latency for about a 14% relative F1 loss.

Honest caveat: for keep1_ext the EM interval [−0.022, +0.000] touches zero. F1 detects a degradation that EM cannot resolve at n = 1000, so we report both.

C3 — 3 joint cells sit on the Pareto front, so C3 is supported by the pre-declared test, but 0 cells dominate the best single-dimension cell. Joint control does not raise the ceiling. It extends the frontier downward in cost, into the region a controller occupies when it is under pressure.

τ = 68 s is the most useful number the project produced. It is the thermal observation delay, and the control law on the previous slide collapsed precisely because its control period was shorter than it. Any thermally aware controller now has a measured value it must exceed.

The 120 s row scores the highest R² and is excluded: 11 points against 3 free parameters flatters itself. What supports the fit is the stability of τ (67–107 s) and of the work coefficient (within 1.6×) while R² swings from 0.11 to 0.69.

C4 — the intercept is credible because two independent routes agree to 7.9%: a regression extrapolated to zero work, and the median of intervals that actually sat at zero work. An earlier trace with no idle periods gave −0.209 W, a device consuming negative power. It was recorded as not reportable and printed with its reasoning. The estimator did not change; the experiment did, to 60 s on and 30 s idle. Retrieval is 19.5% of a query's 131 mJ at the operating point (2.4% minimum, 78.2% maximum); display and radios are about 65% of mean power.

C5 — a negative result, reported as one. Across 27,985 queries interleaved against a tuned static baseline, violations were 1.8% against 1.8% (difference CI [−0.379, +0.257] pp, which includes zero) while the adaptive arm gave up 0.029 recall (CI [−0.0334, −0.0249], which excludes zero). It paid a real cost for no measurable benefit.

The policy is not defective. On the 901 moments where it derated, p95 latency was 43.15 ms against the baseline's 77.56 ms. It chose the wrong moments. Cause: skin temperature peaked at 36.5 °C, so the 42 °C tier never fired. The thermal signal is real and measurable, but not predictive of latency on this workload. A half-width of 0.318 pp means this is a null result, not an underpowered one.

09-09-2026SCOPE14

Conclusion

A runtime control layer for on-device RAG has been built, measured end to end, and is reproducible from a config file and a seed. All 9 modules are complete, 447 tests pass, and 4 of the 5 objectives resolved positively. The fifth resolved negatively, with its cause identified.

The most transferable output is a constant, not a system: τ = 68 s. It bounds how fast any thermally aware controller on this class of device may act, and it explains a failure that the literature would have predicted if the two fields had cited each other.

Two negative results are reported rather than buried, because each one identifies a cause:

  • A published cost model is contradicted by measurement. It omits deserialisation, which dominates on handset flash.
  • A measurable device signal, temperature, is shown not to be predictive of the quantity being controlled on this workload.

Limitations, stated plainly. Generation runs on the host machine, not on the handset, so the on-device half of the system is retrieval. Only one device was used, so the thermal constants are specific to it. C5 was never tested under real throttling.

Project-II. A thermal simulator fitted to the measured trace; a second handset; reduction embeddings precomputed at index time (721 ms cold, 8 ms warm); a fair C5 test under a workload that actually throttles; and on-device generation.
